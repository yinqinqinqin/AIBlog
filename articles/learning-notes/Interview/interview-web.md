# 第一部分：资产制作与材质基础

## 如何提升模型的UV利用率

- 合理排布UV岛
- 重复或对称的部分重叠UV
- 按重要程度非配面积

## 什么时候会用到2U

“2U”一般指**第二套 UV（UV2）**

- 烘培静态光照
  - UV岛不能重叠
  - 保持足够间距
- 同一个模型需要两种不同的贴图映射
- 存储特殊材质数据

## 什么是贴花（Decal）？

贴花是把一张带有 **颜色、法线、粗糙度等信息的纹理投射或覆盖到已有模型表面**，不用修改原模型，就能增加局部细节。

## 次世代场景模型贴图制作需要输出哪些数据？一般几张图？分别放在哪些通道

次世代场景模型贴图分为两类：**烘焙辅助数据**和**最终导入引擎的贴图**

### 最终导入 UE 的贴图

一般是 **3 张基础贴图**

1. BaseColor
2. Normal
3. ORM
   1. ORM = Occlusion + Roughness + Metallic + “ Height/Mask”

## PBR流程通常有两种，简述下两种的区别，现在工作流程最常见的是哪一种，为什么选择这种

1. Metallic / Roughness 金属度工作流
   - Base Color
   - Metallic
   - Roughness
   - Normal
   - AO
2. Specular / Glossiness 高光工作流
   - Diffuse
   - Specular
   - Glossiness
   - Normal
   - AO

现在实时游戏中最常见的是：

> **Metallic / Roughness 金属度工作流。**

### 1. 更符合标准化生产

美术只需要判断：

```
这个区域是金属还是非金属？
```

不需要手动猜测复杂的 Specular 数值，团队资产更容易保持统一。

### 2. 不容易做出错误材质

高光工作流可以随意设置 Specular 颜色，可能把塑料做成彩色反射，产生不符合物理规律的结果。

金属度工作流对参数限制更明确。

### 3. 更节省贴图通道

Metallic 和 Roughness 都是灰度图，可以和 AO 打包到一张 RGB 贴图中。

而 Specular 通常是 RGB 彩色贴图，需要更多纹理数据。

### 4. 更适合 UE 和 Substance 流程

UE、Substance Painter、Megascans 等实时游戏生产流程，对 Metallic/Roughness 的支持非常成熟，资产交换更加方便。

## MatCap的使用原理和应用场景

### 原理

首先把模型法线转换到**观察空间 View Space**，取法线的 X、Y 分量映射成 UV：

```
float3 viewNormal = TransformWorldToView(NormalWS);

float2 matcapUV = viewNormal.xy * 0.5 + 0.5;

float3 color = MatCapTexture.Sample(Sampler, matcapUV);
```

## 一份模型文件会记录哪些顶点数据

模型的常见顶点数据包括顶点位置、法线、切线、多套 UV 和顶点颜色。骨骼模型还会保存骨骼索引和骨骼权重

## 贴图压缩有哪几种方式

| 压缩格式   | 主要用途                | 特点                                 |
| ---------- | ----------------------- | ------------------------------------ |
| BC1 / DXT1 | 无透明 Base Color       | RGB 压缩，约 4 bit/像素              |
| BC3 / DXT5 | 带 Alpha 的颜色贴图     | RGB 与 Alpha 分开压缩，约 8 bit/像素 |
| BC4        | 单通道 Mask、Height、AO | 只保存一个灰度通道                   |
| BC5        | 法线贴图、双通道数据    | 保存 RG，法线的 B 通道运行时重建     |
| BC6H       | HDR 环境贴图            | 支持高动态范围浮点数据               |
| BC7        | 高质量 Base Color、RGBA | 质量高，但编码更复杂                 |
| ASTC       | 移动端通用纹理          | 可选择不同块尺寸，质量与压缩率灵活   |
| ETC2       | Android、移动平台       | 移动端常见标准格式                   |
| PVRTC      | 较早期 Apple 移动设备   | 压缩率高，但细节和边缘质量一般       |

# 第二部分：光照与阴影

## 什么是IBL？实时渲染中IBL影响了光照的哪些部分？

IBL 是 **Image-Based Lighting，基于图像的光照**。

它使用 HDR 环境贴图记录周围各方向的颜色和亮度，让物体能够受到整个环境的照明和反射，而不是只依赖点光、方向光等传统光源。

## 实时渲染中次表面散射有哪些实现方案，并说明优劣

次表面散射（SSS）指光线进入半透明材质内部，经过多次散射后，从附近位置重新射出。

- 屏幕空间次表面散射
- 预积分次表面散射
- 厚度图加透射光

## shadowmap的实现原理

先从光源视角记录场景中离光源最近的表面深度，再从相机视角判断当前像素是否被更靠近光源的物体遮挡。

**Shadow Map 的优缺点**

1. 从光源视角拍摄一张深度图
2. 判断像素点与深度图的大小，判断是否处于阴影中

### 优点

- 原理成熟，硬件支持好
- 可用于动态物体和动态光源
- 与场景几何复杂度相对独立
- 适合方向光、点光和聚光灯
- 可以通过 PCF、PCSS、VSM 等扩展质量

### 缺点

- 分辨率有限，容易出现锯齿
- 存在 Bias 和精度问题
- 光源覆盖范围越大，单位面积精度越低
- 每个投影灯都需要额外渲染阴影几何
- 大量动态光源会增加 Shadow Pass 开销
- 透明物体和复杂半透明阴影较难处理

## AO实现的方式

1. 烘培AO
2. SSAO
3. 顶点AO

## 什么是Cascaded Shadow Maps？解释实时渲染中解决远距离阴影的原理

CSM 全称 **Cascaded Shadow Maps，级联阴影贴图**，主要用于解决**方向光覆盖范围很大时，单张 Shadow Map 精度不足**的问题。

核心思路是：

> 把相机视锥按照距离切成多个区域，每个区域单独生成一张阴影贴图。近处范围小、精度高；远处范围大、精度逐渐降低。

CSM 的主要优缺点

### 优点

- 近距离方向光阴影清晰；
- 可以覆盖较大的相机观察范围；
- 支持动态相机、动态角色和动态场景；
- 技术成熟、兼容性强；
- 可以根据距离合理分配阴影质量。

### 缺点

- 每个 Cascade 都要进行额外阴影绘制；
- 级联边界可能发生跳变；
- 远距离阴影仍然会模糊；
- 相机移动可能造成阴影闪烁；
- 大量植被、WPO 和骨骼模型会让 Shadow Pass 很贵；
- 阴影距离无法无限扩大。

**具体例子**

开放世界中使用方向光模拟太阳：

```
Cascade 0：0～10米
→ 主角、武器、脚底接触阴影

Cascade 1：10～40米
→ 附近建筑、树木、NPC

Cascade 2：40～120米
→ 中距离树林和建筑

Cascade 3：120～300米
→ 远景山体和大型轮廓
```

超过 300 米后可以：

- 不再绘制动态阴影；
- 使用烘焙阴影；
- 使用 Distance Field Shadow；
- 使用云影或低频遮罩近似。

## 什么是动态阴影？是如何实现的？和静态阴影有什么区别？

### 动态阴影（Dynamic Shadow）指：

> **阴影会根据光源、物体、角色和场景的变化，在运行时实时更新。**

### 如何实现的？

最常见的是 **Shadow Map**。

Movable Directional Light + Virtual Shadow Maps

### 什么是静态阴影？

在游戏运行之前，根据固定的灯光和静态模型提前计算出来，并保存到纹理或其他预计算数据中。

静态阴影则提前烘焙到 Lightmap 等数据中，运行时主要进行纹理采样，性能很低且画面稳定，但无法响应灯光或物体变化，并会增加烘焙时间和纹理内存占用。

## 什么是PCF？

PCF 是对 Shadow Map 周围多个 Texel 进行深度比较，再对比较结果求平均，从而把原本二值的硬阴影边缘变成平滑过渡。但普通 PCF 的采样半径通常固定，因此无法表现真实面积光中接触位置硬、远离遮挡物后逐渐变软的效果。

# 第三部分：渲染管线、深度与透明

## 什么是渲染排序

决定不同 Render Pass 以及同一 Pass 内多个物体的绘制先后顺序。

通常先渲染不透明物体，再渲染半透明物体：

不透明物体：通常从近到远

### 物体之间排序正确，但模型内部错误

UE 通常以一个 Primitive 或 Mesh 为单位排序，而不是对每个三角形都精确排序。

如果三角形绘制顺序不正确，可能出现：

- 背面覆盖正面；
- 内外层关系错误；
- 相机转动时透明效果跳变。

这叫 **Self-Sorting Problem**。

| 类型              | 常见绘制顺序     | 深度测试   | 深度写入         | 排序目的         |
| ----------------- | ---------------- | ---------- | ---------------- | ---------------- |
| Opaque            | 近到远           | 开启       | 开启             | 减少 Overdraw    |
| Masked            | 近到远           | 开启       | 开启             | 减少 Overdraw    |
| Alpha Translucent | 远到近           | 通常开启   | 通常关闭         | 保证颜色混合正确 |
| Additive          | 顺序影响较小     | 通常开启   | 通常关闭         | 发光叠加         |
| UI                | 根据层级/Z Order | 视系统而定 | 通常不用场景深度 | 保证界面层级     |

## UE灯光排序

```
场景准备与裁剪
→ 深度 / Nanite可见性
→ DBuffer贴花
→ Base Pass写入GBuffer
→ 准备VSM等阴影数据
→ 计算直接光照
→ Lumen间接光与天空光
→ 反射
→ 天空、大气、体积雾
→ 半透明前向光照
→ 后处理与TSR
→ 最终画面
```

## 半透明渲染有哪几种方案

### 传统混合

```
FinalColor =
    SrcColor * Alpha +
    DstColor * (1.0 - Alpha);
```

### Masked／Alpha Test

```
clip(OpacityMask - Threshold);
```

### 预乘 Alpha

**柔边粒子**，UI，烟雾

```
PremultipliedColor = OriginalColor * Alpha;
```

### Additive 加法半透明

常用**发光**

```
FinalColor = SrcColor + DstColor;
```

## 在渲染管线中，深度测试是什么

深度测试（Depth Test）用于判断：

> 当前准备绘制的像素，是否比深度缓冲中已经记录的像素更靠近相机。

深度缓冲也叫：

- Depth Buffer
- Z-Buffer

决定当前像素通过测试后，是否把自己的深度写入深度缓冲。

| 设置                        | 含义                                   |
| --------------------------- | -------------------------------------- |
| Depth Test 开启             | 检查是否被前方物体遮挡                 |
| Depth Write 开启            | 更新深度缓冲                           |
| Depth Test 开启、Write 关闭 | 能被不透明物体遮挡，但不会遮挡后续物体 |
| Depth Test 关闭             | 无视场景遮挡关系                       |

深度测试是在光栅化过程中，将当前像素的深度与深度缓冲中已有的深度进行比较，以判断当前像素是否被更近的物体遮挡。测试通过后，像素可以输出颜色，并根据 Depth Write 设置更新深度缓冲。不透明物体通常开启深度测试和深度写入；半透明物体通常开启深度测试但关闭深度写入，并依靠从远到近排序完成混合。

## 什么是Forward+？和传统Forward管线有什么区别？

Forward+ 可以理解为：

> **在传统 Forward Rendering 的基础上，先把屏幕划分成很多 Tile / Cluster，并提前计算每个区域受哪些灯光影响，然后真正着色时只遍历这个区域相关的灯光。**

它主要解决传统 Forward 的一个大问题：

> **动态灯光很多时，每个物体/像素都遍历大量灯光，计算浪费严重。**

Forward+ 是对传统前向渲染的优化。传统 Forward 在绘制物体时直接计算影响该物体的动态灯光，当灯光数量很多时容易产生大量无效灯光计算

## 延迟渲染GBuffer中有哪些数据？如何将这些数据组装到MRT到不同通道？

UE4 的延迟渲染会在 Base Pass 中将 BaseColor、World Normal、Metallic、Specular、Roughness、AO、ShadingModelID 和各 Shading Model 的 CustomData 等数据编码到多个 GBuffer Render Target。

为了节省显存和带宽，这些数据会 Packing 到 RGBA 的不同通道，例如经典布局中 GBufferA 主要保存 World Normal，GBufferB 保存 Metallic、Specular、Roughness 和 Shading Model 信息，GBufferC 保存 BaseColor 和 AO，GBufferD 用于 Shading Model 的 CustomData。Base Pass 利用 MRT，一个 Pixel Shader 通过多个 `SV_Target` 一次性把这些数据写入多张 Render Target，后面的 Deferred Lighting 再读取并 Decode 成 GBufferData

# 第四部分：屏幕空间与后处理

## 卡通渲染描边有哪些实现方案

1. 反向外壳描边 Inverted Hull
   - 复制一层模型，沿顶点法线向外膨胀，渲染背面并使用黑色材质。
   - 优点：轮廓稳定，角色描边效果好。
   - 缺点：硬边、法线断裂处容易炸开；远近描边粗细不一致；增加一次模型渲染。
2. 后处理深度描边
   - 比较当前像素与周围像素的 Scene Depth：
   - 优点：不需要修改模型，整个场景都能使用。
   - 缺点：同一平面内部结构检测不到；透明物体支持较差；远处容易变细或闪烁。
3. 后处理法线描边
   - 比较当前像素和周围像素的世界法线：
   - 优点：能产生内部结构线。
   - 缺点：法线贴图噪声可能产生杂乱描边，需要设置阈值。
4. Custom Depth / Stencil 描边
   - 优点：可以精确控制哪些物体描边。

## 实时渲染主流抗锯齿的方法有哪些？

实时渲染把连续的三维场景采样到离散屏幕像素中，采样不足会产生：

- 模型轮廓阶梯
- 细小几何闪烁
- 纹理摩尔纹
- 高光和法线闪烁
- 远处物体抖动

```
空间采样：SSAA、MSAA
屏幕后处理：FXAA、SMAA
时间采样：TAA、TSR、TAAU
```

### SSAA：超级采样抗锯齿

SSAA 会用高于最终输出的分辨率渲染，再缩小到目标分辨率。

#### 优点

- 抗锯齿质量非常高
- 不只处理模型边缘
- 也能改善纹理、透明度、高光和 Shader 锯齿
- 原理简单，结果稳定

#### 缺点

- 性能成本极高
- 宽高放大两倍，像素数量会变成四倍
- 显存、带宽和后处理成本都会增加

### MSAA：多重采样抗锯齿

它在一个像素内部保存多个覆盖率和深度采样点，但通常不会为每个采样点都完整执行一次像素 Shader。

#### 优点

- 模型几何边缘清晰
- 不容易让整个画面变模糊
- 没有 TAA 的历史拖影
- 对 VR、前向渲染和高清 UI 比较友好

#### 缺点

主要只解决**几何轮廓锯齿**，对以下问题帮助有限：

- 法线贴图闪烁
- 高光锯齿
- Shader 程序化边缘
- 纹理摩尔纹
- 半透明内部锯齿

### FXAA：快速近似抗锯齿

FXAA 是一种全屏后处理方案。

它不增加几何采样，而是在最终画面中寻找亮度变化明显的边缘，然后沿边缘方向进行平滑。

#### 优点

- 性能成本很低
- 实现简单
- 不依赖运动向量和上一帧画面
- 能用于几乎所有渲染管线

#### 缺点

FXAA 不知道边缘来自模型还是纹理，只看到最终颜色，因此容易：

- 模糊文字和 UI
- 模糊纹理细节
- 画面整体偏软
- 无法稳定解决远处细线闪烁
- 运动时仍可能出现像素爬动

### SMAA：增强形态学抗锯齿

SMAA 和 FXAA 类似，也属于屏幕后处理抗锯齿，但会使用更复杂的边缘和图案识别。

#### 优点

- 通常比 FXAA 更清晰
- 对斜线和规则几何边缘识别更准确
- 没有普通 TAA 的拖影
- 成本仍低于高倍 MSAA 和 SSAA

#### 缺点

- 成本高于 FXAA
- 仍然主要处理当前帧
- 无法彻底解决细小几何和高光的时间闪烁
- 对复杂噪声边缘效果有限

### TAA：时间抗锯齿

TAA 全称 **Temporal Anti-Aliasing**，是现代实时渲染非常常见的方案。

它通过每帧轻微移动投影采样位置，收集不同子像素信息，再把当前帧与历史帧结合。

#### 优点

- 能处理几何轮廓
- 能缓解纹理、高光和 Shader 闪烁
- 对细小几何和远景稳定性较好
- 单帧采样成本相对可控

#### 缺点

历史数据不准确时可能产生：

- 拖影
- 鬼影
- 画面模糊
- 透明物体残影
- WPO 动画拖尾
- 镜头切换时历史错误

### UE5 主要使用哪种抗锯齿？

#### 默认延迟渲染：TSR

它通过当前帧、历史帧、运动向量、深度和投影抖动来稳定锯齿，并把较低的内部渲染分辨率重建到输出分辨率。比较适合 Nanite、Lumen 和高分辨率游戏。

TSR 同时完成：

```
时间抗锯齿
+
低分辨率画面上采样
+
细节重建
```

其中 **MSAA 只支持前向渲染路径**，不适合 UE 默认的延迟渲染。

## 简单阐述实时渲染中动态模糊效果的实现原理

在运行时，对当前帧的屏幕进行多次采样，根据权重得到模糊效果

- Mask局部模糊
- 景深
  - 先根据 Scene Depth 判断每个像素离焦平面有多远，再计算这个像素应该模糊多少，最后对离焦区域做邻域采样。
- 根据速度动态模糊
  - 所以 Motion Blur 本质是：

    > **沿 Velocity 方向进行方向性邻域采样。**

## 实时渲染中有哪些屏幕空间技术？有什么优缺点？

### SSR

#### 优点

- 完全动态
- 能反射当前屏幕中的角色、动态物体
- 不需要重新渲染一次场景
- 比 Planar Reflection / Ray Tracing 便宜

#### 缺点

最大问题：

```
屏幕外没有数据
→ 无法反射

被其他物体挡住
→ 没有数据
→ 无法反射
```

所以经常出现：

- 屏幕边缘反射消失
- 相机转动时反射突然出现/消失
- 薄物体穿透

### SSAO / GTAO：屏幕空间环境光遮蔽

#### 优点

- 完全动态
- 不需要 Lightmap
- 不需要 Distance Field
- 对接触细节效果明显
- 延迟渲染已有 Depth / Normal，可以直接使用

#### 缺点

仍然是屏幕空间：

```
屏幕外几何
→ 不知道

被遮挡几何
→ 不知道
```

容易出现：

- Halo 黑边
- 屏幕边缘 AO 消失
- 噪点
- 时域拖影

### SSGI：屏幕空间全局光照

#### 优点

- 动态
- 可以产生颜色溢出
- 不需要完整光追
- 成本低于完整 GI

#### 缺点

- 屏幕外没有 GI
- 被遮挡表面没有信息
- 容易漏光
- 噪点、拖影
- 大尺度 GI 不可靠

因此现代方案通常不会只依赖 SSGI。例如 Lumen 也会优先进行 Screen Trace，再使用其他数据补充。

### Contact Shadow / Screen Space Shadow

#### 优点

- 小尺度阴影非常清晰
- 不需要提高整张 Shadow Map 分辨率
- 很适合补充 VSM / CSM

#### 缺点

- 距离不能太长
- 屏幕外遮挡物无效
- 可能出现噪点、断裂
- 大范围阴影不适合

### Screen Space Refraction / Distortion

#### 优点

- 很便宜
- 动态
- 水面、玻璃、热浪效果明显

#### 缺点

- 只能扭曲已经存在于屏幕里的背景
- 屏幕边缘容易穿帮
- 不能表现真正厚度
- 不是严格物理折射

### 屏幕空间描边

#### 优点

- 不增加模型几何
- 能画内部结构线
- 可控制指定角色
- 后处理统一处理

#### 缺点

- 依赖屏幕分辨率
- 远近描边粗细需要处理
- 深度接近时可能漏边
- 法线噪声可能产生额外线条

## 性能影响的指标

| 指标           | 主要影响                       |
| -------------- | ------------------------------ |
| Draw Call 数量 | CPU、Render Thread、RHI Thread |
| 顶点数量       | GPU Vertex Shader、蒙皮、WPO   |
| 像素覆盖面积   | GPU Pixel Shader               |
| Shader复杂度   | GPU计算和纹理采样              |
| Overdraw       | GPU重复像素计算                |

## 什么是drawcall？drawcall数量一般和什么有关系？

CPU 向 GPU 提交的一次绘制命令，通知 GPU 使用指定的模型、材质和渲染状态绘制一批三角形。

```
Draw Call 数量
≈ 可见物体数量
× Mesh Section / 材质槽数量
× 参与的渲染 Pass 数量

再受到实例化、合批、LOD 等因素影响。
```
